# RAG(Retrieval-Augmented Generation) 학습 노트

> devlog-llm STRATEGY.md Phase 3에서 필요해질 개념. 실제로 구현하기 전에 미리 정리해두는 메모.

## 왜 필요한가

LLM은 두 가지 한계가 있다.

1. **학습 시점 이후 정보를 모른다** — 그리고 애초에 내 블로그 글이나 나눈 대화 같은 개인 데이터는 학습한 적이
   없다.
2. **모르면서도 그럴듯하게 답한다** (hallucination).

이걸 해결하는 두 가지 방법이 있는데:

- **Fine-tuning**: 모델 자체를 내 데이터로 재학습. 비용·시간이 크고, 데이터가 바뀔 때마다 다시 학습해야 함.
- **RAG**: 모델은 그대로 두고, 질문할 때마다 관련 자료를 "찾아서" 프롬프트에 끼워넣어 준다. 데이터를
  최신으로 유지하기 훨씬 쉬움.

devlog-llm의 가설(`PLANNING.md`) — "AI를 잘 쓰는 패턴은 기록·분석하면 재사용 가능한 지식이 된다" — 을
실제로 검증하려면, 기록한 글·대화를 "검색해서 답변에 활용"하게 만들어야 한다. 그게 RAG 파트가 하는 일.

## 전체 파이프라인

### 1. 인덱싱 (미리 준비)

- **Chunking** — 글/대화를 통째로 넣지 않고 작은 단위(문단, 또는 N토큰)로 쪼갠다. 너무 크면 검색 정확도가
  떨어지고, 너무 작으면 맥락이 끊긴다.
- **Embedding** — 각 chunk를 임베딩 모델에 통과시켜 숫자 벡터(예: 1536차원)로 변환. 핵심 아이디어는
  "의미가 비슷한 텍스트는 벡터 공간에서 가까이 위치한다."
- **저장** — 벡터 + 원문 + 메타데이터(`source_type`, `source_id` 등)를 벡터DB에 저장. devlog-llm은
  Supabase의 pgvector 사용 예정 (`docs/DB_ROADMAP.md` Phase 3 참고).

### 2. 질의 임베딩

사용자가 질문하면, 그 질문도 인덱싱 때와 **같은** 임베딩 모델로 벡터화한다.

### 3. 검색 (Retrieval)

질문 벡터와 저장된 chunk 벡터들의 유사도(보통 cosine similarity)를 계산해서 가장 가까운 상위 k개
(top-k)를 뽑는다. pgvector는 `<->`(L2 거리), `<=>`(코사인 거리) 연산자로 SQL에서 바로 유사도 검색이
가능하다.

### 4. 증강 (Augmentation)

찾아온 chunk 원문을 LLM에게 보낼 프롬프트의 컨텍스트로 끼워넣는다 ("다음은 참고 자료입니다: ...").

### 5. 생성 (Generation)

LLM(devlog-llm은 Groq)이 원래 질문 + 끼워넣은 참고 자료를 보고 답변을 생성한다. 어떤 글/대화를 근거로
답했는지 출처 링크를 같이 보여주면 신뢰도가 올라간다 (`STRATEGY.md` Phase 4에 이미 계획돼 있음).

## 핵심 용어

| 용어 | 의미 |
|---|---|
| Embedding | 텍스트를 의미를 반영한 고정 길이 숫자 벡터로 변환한 것 |
| Vector DB | 벡터를 저장하고 유사도 검색을 빠르게 해주는 저장소 (pgvector, Chroma, Qdrant 등) |
| Chunk / Chunking | 원문을 검색 단위로 쪼갠 조각 / 쪼개는 작업 |
| Cosine similarity | 두 벡터의 방향이 얼마나 비슷한지 (-1~1, 1에 가까울수록 유사) |
| Top-k | 검색 결과 중 가장 유사한 상위 k개만 쓰는 것 |
| 폴리모픽 참조 | 컬럼 하나(`source_id`)가 여러 종류의 부모 테이블 중 하나를 가리키는 설계 (`DB_ROADMAP.md` Phase 3 옵션 A) |

## RAG vs Fine-tuning

| | RAG | Fine-tuning |
|---|---|---|
| 데이터 최신화 | 벡터DB에 새 글만 추가하면 즉시 반영 | 재학습 필요 (비용·시간) |
| 비용 | 임베딩 비용만 (상대적으로 저렴) | GPU 학습 비용 |
| 모델 자체 | 안 바뀜 | 가중치가 바뀜 |
| 적합한 경우 | 자주 바뀌거나 개인화된 지식 | 말투·형식·도메인 능력 자체를 바꾸고 싶을 때 |

## 임베딩 모델 최근 동향

[RAG를 통해 LLM을 꽃 피우게 하는 조연 '임베딩 모델'은 어떻게 흐르고 있을까](https://introduce-ai.tistory.com/entry/RAG%EB%A5%BC-%ED%86%B5%ED%95%B4-LLM%EC%9D%84-%EA%BD%83-%ED%94%BC%EC%9A%B0%EA%B2%8C%ED%95%98%EB%8A%94-%EC%A1%B0%EC%97%B0-%E2%80%98%EC%9E%84%EB%B2%A0%EB%94%A9-%EB%AA%A8%EB%8D%B8%E2%80%99%EC%9D%80-%EC%96%B4%EB%96%BB%EA%B2%8C-%ED%9D%98%EB%9F%AC%EA%B0%80%EA%B3%A0-%EC%9E%88%EC%9D%84%EA%B9%8C) — 이 글이 정리한 RAG 4단계(문서 벡터화→질문 벡터화→유사도 검색→LLM 응답)는 위 파이프라인과 정확히 같음. 임베딩 모델 자체는 "조연이지만 검색 품질을 좌우하는" 역할이라는 요지, 그리고:

- **Decoder 기반(LLM 기반) 임베딩** — ChatGPT 이후 등장, 기존 Encoder(BERT류) 기반보다 성능 우위
- **MRL(Matryoshka Representation Learning)** — 벡터 차원을 줄여도 성능을 최대한 유지하는 학습 기법.
  Voyage AI `voyage-4-lite`가 바로 이 방식이라 1024(기본)~2048~256차원까지 유연하게 쓸 수 있음 — 임베딩
  모델 후보 조사에서 유력 후보로 남겨둔 이유 중 하나
- **다중 기법 앙상블** — `BGE-m3`처럼 빈도 기반(sparse) + Dense 벡터 + Multi-vector 방식을 함께 쓰는 모델도
  등장. devlog-llm 후보에선 Render 무료 티어 제약으로 셀프호스팅 오픈소스 모델 자체를 제외했지만, 참고용으로
  기억해둘 것

## RAG vs Agent AI

RAG는 Agent가 아니다 — 흔히 헷갈리는 지점이라 정리해둔다.

| 단계 | 특징 |
|---|---|
| 단일 LLM 호출 | 요청 1번 → 응답 1번. 지금 `/chat`이 여기 |
| **Workflow** | 여러 단계를 **코드가 미리 정해둔 순서대로** 실행 — **RAG가 여기 속함** (검색→증강→생성 순서 고정) |
| Agent | **LLM 스스로**가 다음에 뭘 할지 판단하며 여러 단계·도구를 자율적으로 선택 |

RAG는 "검색 → 프롬프트에 끼워넣기 → 생성"이 항상 같은 순서로 코드가 실행하는 고정 파이프라인이다. LLM이
스스로 "이 질문엔 검색이 필요한지, 어떤 도구를 쓸지"를 판단해서 반복적으로 움직이는 게 아니므로 Agent가
아니다. devlog-llm이 실제로 Agent가 되려면 예를 들어 "블로그 검색이 필요한지 LLM이 스스로 판단하고, 필요하면
검색하고, 웹 검색 같은 다른 도구도 스스로 선택해서 부르는" 구조가 필요한데 — 지금 계획(STRATEGY.md
Phase 1~4)엔 그런 부분이 없다.

## devlog-llm에서 실제로 정해야 할 것들 (미리보기)

- 임베딩 모델 선택 — 조사는 끝났고 결정만 보류 중. 무료 우선 조건에서 Voyage AI `voyage-4-lite`
  (카드 불필요, 200M 토큰 무료, 한국어 지원)가 유력 후보. 비교표는 `docs/DB_ROADMAP.md` Phase 3 참고.
  이 모델이 확정되면 벡터 차원(N)도 같이 정해짐 (voyage-4-lite 기본 1024차원)
- Chunking 전략 — 포스트는 문단 단위? 대화는 턴 단위, 아니면 세션 전체?
- 테이블 설계 — 통합 vs 소스별 분리 (`docs/DB_ROADMAP.md` Phase 3의 A/B 옵션)
- top-k 값, 그리고 "관련 없는 결과까지 끼워넣지 않기 위한" 최소 유사도 임계값
